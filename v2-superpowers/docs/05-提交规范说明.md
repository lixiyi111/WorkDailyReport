# 提交规范说明（两阶段）

> 日期：2026-11-26
> 结论：**不改写已推送的 v1 历史**；两阶段各自遵守本阶段的提交约定。

## 1. 阶段一（v1-SDD）

- 格式：`feat(v1): ...` / `fix(v1): ...` / `docs(v1): ...` / `chore(v1): ...`
- 划分：按 SDD 阶段任务（需求定义、架构设计、接口契约、任务拆解、代码生成、验证交付）组织。
- 示例：`feat(v1): 增加 JWT 登录与角色权限`
- 历史：已推送到 `origin/master`（截至 `463dc78`），保留原样，不重写。

## 2. 阶段二（v2-Superpowers）

- 格式：`feat|fix|test|docs: [V2-xxx] 一句话说明`
- 划分：一次提交对应一个 V2 任务（见 [04-v2-tasks.md](04-v2-tasks.md)）。
- 示例：`feat: [V2-040] 实现日报编排、幂等落库与推送`
- 历史：从 `9a3ece6`（V2-000）起共 34 个提交，全部符合；尚未推送。

## 3. 为什么不统一改写

1. 改写会重写后续所有提交哈希，`v1-sdd` tag 与文档里引用的提交号都会失效；
2. 已推送历史需要 `force-push`，会覆盖远程；
3. 课程把提交历史作为证据，事后批量修改提交信息有「伪造提交历史」的风险；
4. 两阶段方法不同，提交格式不同本身就是真实过程的一部分，答辩时可以解释。

## 4. 检查命令

```bash
# 阶段二提交应全部符合；无输出即通过
git log --format=%s 463dc78..HEAD | grep -vE '^(feat|fix|test|docs): \[V2-[0-9]{3}\] ' || true
```

## 5. 后续约定

- 第 4 周变更涟漪继续用阶段二格式，例如 `feat: [V2-070] 增加飞书考勤采集`；
- v2 推送前先跑上面的检查命令；
- 阶段一历史保持原样，如果报告需要对照，可引用本文件说明两阶段格式差异。
