# 方法切换回顾（第 3 周）

> 时间：2026-11-26
> 阶段：阶段一（SDD）→ 阶段二（Superpowers）
> 用途：项目总结报告「过程回顾」章素材；本阶段起专一使用 Superpowers 工作流。

## 1. 阶段一的真实体验

第 1–2 周按 SDD 六阶段推进：proposal → design → 接口契约 → tasks → 代码生成 → 验证交付。

最大的感受是「慢在前、快在后」。写 proposal 与 design 花的时间最多，但进入编码后几乎不需要反复解释背景：AI 每次都能对着固定的 `S1–S9`、`IR-1–IR-10`、`F/P/B` 编号工作，生成的代码与契约的偏差明显更少。红队评审也确实在编码前发现了几个边界场景（跨零点、重复采集、无数据成员），这些问题如果留到编码后修，返工成本会高得多。

代价也很明显：需求一变，就要同步改 proposal、design、tasks 三份文件；小改动也容易被流程拖慢；而且文档质量高度依赖写规范的人，写漏了，AI 就会在实现里「自由发挥」。

## 2. 两种方法对比

| 维度 | SDD（阶段一） | Superpowers（阶段二） |
|------|---------------|------------------------|
| 优势 | 规范先行，需求、设计、任务、测试可逐级追溯；ADR 把选型理由固定下来；适合多人协作，答辩时能讲清「为什么这么做」 | 把「怎么做」固化成可执行纪律：brainstorming 逼出隐含需求，writing-plans 强制验收标准，TDD 强制先红后绿，code-review 强制逐条回应；节奏快，适合与 AI 结对 |
| 局限 | 前期文档成本高；需求变更要同步维护三份规范；小改动容易被流程拖慢；规范写漏时 AI 会自行补全 | 流程依赖技能触发与人的自律，触发不到就容易退回 Vibe Coding；规范产物不如 SDD 完整，追溯性要靠人补；任务拆得不好会变成「为流程而流程」 |
| 适用场景 | 需求相对稳定、交付物要接受评审、多人协作、需要强追溯的项目 | 需求边做边澄清、单人 + AI 快速迭代、需要持续重构与回归的项目 |

## 3. 本项目的切换决定

- v2 从零重写，不复制 `v1-sdd` 下任何源代码；
- 只把阶段一的设计结论（ADR、接口契约、表结构经验）以**文字**带入，作为重做的参考，不作为起点代码；
- v2 按 `writing-plans → executing-plans → test-driven-development → code-review` 推进；
- 每个任务先写失败测试（红），再写最小实现（绿），再重构；
- 每个任务一次提交，提交信息带任务编号；
- 每个任务完成前做一次 code-review，评审意见逐条回应或修复。

## 4. 一句话结论

SDD 解决「想清楚」，Superpowers 解决「做得稳」。前者产出可评审的规范，后者产出可验证的小步提交；两者不是替代关系，而是同一项目的两种约束方式。阶段二用 v1 的规范结论当输入，用 Superpowers 的纪律当过程约束，正好可以观察「同一需求、不同方法」的差异。
