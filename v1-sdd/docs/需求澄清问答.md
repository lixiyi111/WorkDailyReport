# 需求澄清问答记录

> 阶段：第 1 周 · 需求澄清
> 说明：本记录根据“团队日报”结构化提问整理，结论已同步到 [../specs/proposal.md](../specs/proposal.md)。提交前请本人逐条复核。

| 编号 | 问题 | 确认结论 |
|------|------|----------|
| Q1 | 谁会看日报？ | 成员看本人日报与团队日报；组长看全组并负责汇总；导师只读团队日报。 |
| Q2 | 需要区分权限吗？ | 需要，分为成员 / 组长 / 导师三级：成员仅本人，组长全组，导师只读团队日报。 |
| Q3 | 日报是自动推送还是按需查询？ | 团队日报每日 18:30 自动推送；个人日报在 Web 端查看和编辑；Web 端支持随时查询。 |
| Q4 | GitHub 具体采集哪些数据？ | 以 commit 为主，关联 PR / issue；支持多仓库（v1 默认 3 个）；公有、私有仓库均可（只读令牌）。 |
| Q5 | 飞书具体采集哪些？ | 任务创建与状态流转、指定群的群消息；日程、审批、考勤不在 v1 范围。 |
| Q6 | 还要不要接其他来源？ | v1 只接 GitHub、飞书、SMTP；邮件仅作为推送渠道，不作为数据源。 |
| Q7 | 采集时间窗口怎么算？ | 自然日 00:00–24:00（Asia/Shanghai）；跨零点提交按时间戳归入对应自然日。 |
| Q8 | 多平台用户怎么对应到同一成员？ | 以邮箱为主键，自动匹配 GitHub 邮箱 / 用户名、飞书邮箱 / open_id；未命中时人工绑定兜底。 |
| Q9 | 个人日报写到什么粒度？ | 按任务 / 模块归类，commit 合并成条目；包含「今日完成 / 协作贡献 / 问题与阻塞 / 明日计划」。 |
| Q10 | 团队日报是拼接还是重新归类？ | 不是简单拼接：按项目 / 模块归类、去重，并生成团队概览统计。 |
| Q11 | 日报格式固定吗？ | 固定 Markdown 模板与字段，Web 端渲染展示。 |
| Q12 | 生成后允许人工修改吗？ | 允许；修改保存为日报新版本，原始采集数据只读保留，便于追溯与重新生成。 |
| Q13 | 协作成果怎么归属？ | commit 作者为主归属，PR reviewer 记为协作贡献；任务以负责人为主、参与人记协作贡献；按角色记录，不做比例拆分，避免重复计入。 |
| Q14 | 只在群里讨论、没提交代码的人怎么体现？ | 有效讨论 / 评审按条记为协作贡献，不计为代码产出。 |
| Q15 | 帮别人 review、答疑算不算产出？ | 算，计入协作贡献条目。 |
| Q16 | 当天无数据怎么写？ | 输出「无产出」，不空白、不报错。 |
| Q17 | 请假、周末、节假日怎么处理？ | 可标注「请假 / 节假日」，不计为异常；周末按正常日期处理，可配置跳过。 |
| Q18 | 数据源失效怎么办？ | 降级为部分生成，明确标注缺失数据源；优先使用最近缓存，整体不崩溃。 |
| Q19 | 推送时间、渠道？ | 次日 09:00 生成并推送前一自然日的团队日报，渠道为邮件 + 飞书机器人；个人日报在 Web 端查看。 |
| Q20 | 历史日报存多久？ | 长期保存，v1 不设自动清理；支持按日期 / 成员查询与重新生成。 |
| Q21 | v1 明确不做什么？ | 不做 LLM 摘要、考勤采集、多团队 / 多租户、移动端、复杂可视化。 |
