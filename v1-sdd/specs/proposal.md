# 智能日报生成器 · 需求规范（proposal.md）

> 版本：v1.0
> 阶段：第 1 周 · 需求定义
> 状态：已定稿（关键决策已确认，待组内评审）
> 关联：课程指导书 [../docs/classneed.md](../docs/classneed.md)

## 1. 项目名称

智能日报生成器（团队日报自动化）

## 2. 背景

团队日报是每个成员的日常负担，目前主要靠手工完成，存在五个痛点：

1. 下班时靠回忆当天做了什么，容易遗漏；
2. 工作痕迹散落在 GitHub 提交、飞书任务、群聊消息等多个平台，需要逐个复制；
3. 忙起来只写「记得住的」，而不是真实做过的；
4. 多人协作的接口修改、缺陷修复难以归属到具体成员；
5. 各人格式不统一，组长还要手工汇总团队日报。

本系统通过 GitHub API、飞书开放平台与 SMTP，自动采集真实工作数据，生成个人日报并汇总为格式统一的团队日报，降低编写与汇总成本。

## 3. 目标（可度量）

- **G1 编写耗时**：成员每日用于编写 / 校对日报的时间 ≤ 5 分钟（基线以组内 3 个工作日实测为准）。
- **G2 条目完整率**：日报条目对当日实际工作记录的覆盖率 ≥ 95%（以人工抽查 3 个工作日为样本）。
- **G3 汇总耗时**：10 人团队日报的生成与推送 ≤ 1 分钟（不含外部接口限流等待）。
- **G4 协作归属**：多人协作产生的工作记录 100% 能按规则归属到至少一名成员，重复计入 0 条。
- **G5 可追溯**：日报中每条条目均可回溯到原始数据（commit SHA / 任务 ID / 消息 ID），追溯率 100%。

## 4. 范围

### 4.1 做什么（逐条编号，供用例追溯）

| 编号 | 功能 | 说明 |
|------|------|------|
| S1 | 采集 GitHub 提交 | 采集指定仓库在时间窗口内的 commit：作者、时间、仓库、分支、message、SHA，以及关联的 PR / issue；支持多仓库。 |
| S2 | 采集飞书任务 | 采集任务创建与状态流转：任务 ID、标题、负责人、参与人、状态、变更时间。 |
| S3 | 采集飞书群消息 | 采集指定群的成员发言：发送人、时间、内容摘要、消息 ID；仅采集配置的群。 |
| S4 | 成员身份映射 | 把 GitHub 账号、飞书账号、邮箱映射到同一成员；支持人工绑定与修正。 |
| S5 | 生成个人日报 | 按日汇总提交、任务、消息，按任务 / 模块归类，输出「今日完成 / 协作贡献 / 问题与阻塞 / 明日计划」。 |
| S6 | 汇总团队日报 | 按统一模板汇总全组成员，归类去重，生成团队概览与成员摘要。 |
| S7 | 推送日报 | 通过 SMTP 邮件与飞书机器人推送个人 / 团队日报，记录发送结果。 |
| S8 | 存储与查询 | 日报与原始采集数据存入 MySQL，支持按日期 / 成员查询与重新生成。 |
| S9 | Web 界面 | 查看个人 / 团队日报，手工编辑并保存；编辑不影响原始采集数据。 |

### 4.2 不做什么（本期明确排除，逐条给出理由）

- **N1 不做 LLM 智能摘要 / 自动改写**：v1 采用确定性规则模板，保证结果可复现、可审查；智能摘要留到后续版本。
- **N2 不做考勤数据采集**：按课程安排留到 v1.1 的变更演练。
- **N3 不做多团队 / 多租户与组织级权限**：v1 只服务单个小组，权限限定为成员 / 组长 / 导师三级。
- **N4 不做移动端与多端适配**：v1 只提供 Web 端与邮件 / 飞书推送。
- **N5 不做复杂可视化报表与数据大屏**：v1 只提供基础统计（提交数、完成任务数、参与人数）。

## 5. 技术约束

- **语言 / 运行时**：Python 3.12
- **后端框架**：FastAPI + Uvicorn
- **前端**：Vue 3 + Vite
- **数据库**：MySQL 8（aiomysql + SQLAlchemy）
- **外部接口**：GitHub REST API、飞书开放平台、SMTP
- **运行环境**：conda 环境 `work_daily`（Windows 11 本地）
- **时区**：Asia/Shanghai
- **凭证**：仅通过环境变量 / `.env` 注入，不入库、不入仓

## 6. 成功标准

### 6.1 功能验收

| 编号 | 验收标准（可度量） | 验证方式 |
|------|--------------------|----------|
| F1 | 指定仓库、指定时间窗口内的 commit 采集覆盖率 100%，条数与 GitHub API 返回一致 | 对照 API 分页结果逐条比对 |
| F2 | 飞书任务及状态流转字段完整率 100%（任务 ID、负责人、状态、时间齐全） | 抽查 20 条任务记录 |
| F3 | 指定群消息按发送人与时间正确归类，抽样 50 条准确率 ≥ 95% | 人工抽样标注比对 |
| F4 | 每个有数据的成员生成 1 份个人日报，提交 / 任务 / 消息三类条目均有映射，条目可追溯率 100% | 随机抽 10 条条目回溯原始 ID |
| F5 | 团队日报覆盖全部有数据成员，格式统一，含团队概览与成员摘要；同一窗口重复生成结果一致 | 连续生成 2 次比对结构 |
| F6 | 凭证有效、网络正常时，邮件与飞书机器人发送成功率 100%，失败有日志 | 发送测试日报并检查送达与日志 |
| F7 | 日报与原始数据入库；按日期 / 成员查询结果正确；重复运行不产生重复条目 | SQL 查询 + 重复运行对比 |
| F8 | Web 端可查看、编辑并保存日报；保存后原始采集数据不变 | 编辑后比对原始表 |

### 6.2 性能验收

| 编号 | 验收标准 | 验证方式 |
|------|----------|----------|
| P1 | 单日 10 名成员、3 个仓库的采集 + 个人日报生成 ≤ 60 秒（不含外部限流等待） | 计时脚本 |
| P2 | 10 人团队日报汇总 ≤ 10 秒 | 计时脚本 |
| P3 | 日报列表 / 详情 API 响应 P95 < 500ms（本地 MySQL） | 压测 / 日志统计 |
| P4 | 连续 7 天运行，重复条目数为 0 | 数据比对 |

### 6.3 边界场景

| 编号 | 场景 | 预期行为 |
|------|------|----------|
| B1 | 成员当天无任何数据 | 输出「无产出」，不空白、不报错 |
| B2 | 请假 / 法定节假日 | 可标注「请假 / 节假日」，不计为异常 |
| B3 | 数据源失效（token 过期 / 限流） | 降级为部分生成，明确标注缺失的数据源，整体不崩溃 |
| B4 | 同一 commit / 消息被重复采集 | 不重复计入，日报条目保持唯一 |
| B5 | 提交跨零点 | 按提交时间戳归入正确的自然日 |
| B6 | 成员身份未映射 | 数据保留并标记「未归属」，支持人工绑定后重新生成 |

## 7. 术语定义

- **个人日报**：以单个成员为对象、按日汇总其工作产出的结构化记录。
- **团队日报**：将全组成员个人日报按统一模板汇总后的结果。
- **协作成果**：由多人共同完成、需要归属到多个成员的提交、任务或评审行为。
- **归属**：把一条工作记录判定为某个成员产出的规则。
- **时间窗口**：自然日 00:00–24:00（Asia/Shanghai），跨零点按时间戳归属。
- **幂等**：同一数据重复采集或重复生成时，不产生重复条目。
- **降级**：某个数据源不可用时，使用缓存或部分数据继续生成，并标注缺失。
- **未归属**：无法映射到具体成员的工作记录，保留原始数据并等待人工绑定。

## 8. 被问出来的隐含需求

> 以下需求在最初的一句话需求中没有写明，是在围绕「团队日报」做结构化澄清时被问出来的。完整问答见 [../docs/需求澄清问答.md](../docs/需求澄清问答.md)，编号用于 design.md / tasks.md 追溯。

| 编号 | 隐含需求 | 来源问题 | 为什么必须写进规范 | 关联范围 |
|------|----------|----------|--------------------|----------|
| IR-1 | **多平台成员身份映射**：GitHub 账号、飞书账号、邮箱要能对应到同一成员 | Q8 | 不打通身份，采集到的提交与任务无法归到具体人，个人日报无法生成 | S4 |
| IR-2 | **采集去重与幂等**：同一 commit / 同一条消息重复采集不得重复计入 | Q4、Q5 | 定时任务重跑、接口翻页会产生重复条目，导致日报虚高 | S1、S3、S8 |
| IR-3 | **协作成果归属规则**：明确 commit 作者、PR reviewer、任务负责人、讨论参与者各自的归属与权重 | Q13–Q15 | 原需求只说「自动归属」，没有规则就无法实现，也容易引发组内争议 | S5、S6 |
| IR-4 | **统计时间窗口**：明确按自然日还是滚动窗口统计，处理跨零点提交与时区 | Q7 | 「每日」默认自然日，但加班提交常跨零点，口径不清会漏算或重算 | S1、S2、S3、S5 |
| IR-5 | **无数据与缺勤表达**：当天无提交 / 无任务时输出「无产出」，请假、节假日单独标注 | Q16、Q17 | 空白或报错会让团队日报不完整，也无法区分「没干活」和「请假」 | S5、S6 |
| IR-6 | **人工修正与原始数据留痕**：日报允许人工修改，但保留原始采集数据以支持追溯和重新生成 | Q12 | 自动生成不可能百分百准确，必须可回退、可审计 | S8、S9 |
| IR-7 | **可见范围与隐私脱敏**：按成员 / 组长 / 导师区分日报可见范围，群消息中的隐私内容需脱敏 | Q1、Q2 | 日报包含提交与群聊内容，涉及隐私，不能全员无差别可见 | S3、S9 |
| IR-8 | **推送失败重试与状态记录**：邮件 / 飞书推送失败要重试，并记录成功或失败结果 | Q19 | 推送是最后一公里，失败不能被静默吞掉 | S7 |
| IR-9 | **历史存储与查询**：日报按日期、成员持久化，支持查询历史与重新生成 | Q20 | 没有历史就无法对比、审计和补发 | S8 |
| IR-10 | **数据源降级**：token 失效 / 接口限流时使用缓存或 mock 数据部分生成，并提示数据不完整 | Q18 | 外部接口不稳定，不能因单个数据源失败导致整份日报失败 | S1、S2、S3 |

## 9. 关键决策（原待确认项）

- **D1 Web 界面**：v1 提供 Web 界面（查看 + 编辑），不做移动端。
- **D2 团队日报模板**：采用「团队概览 + 成员摘要 + 协作成果 + 风险与阻塞」四段式。
- **D3 身份映射**：以邮箱为主键自动匹配 GitHub / 飞书账号，未命中时人工绑定兜底。
- **D4 统计窗口**：自然日 00:00–24:00（Asia/Shanghai），跨零点按时间戳归属。
- **D5 推送**：每日 18:30 生成并推送团队日报，渠道为邮件 + 飞书机器人。
- **D6 降级**：数据源不可用时部分生成并明确提示，不整体失败。
- **D7 生成方式**：采用确定性规则模板，不使用 LLM 摘要。
